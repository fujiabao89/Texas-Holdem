| **F-01** | CodeRabbit（PR 会话）：无冠军终局在内存快路径中会再次显示冠军 | **有效**。`snapshotChampionPlayerId` 原先仅排除了 `WITHDRAWN` 玩家。在合法的无冠军终局（如 `tournament-result-read.test.ts:153`：剩余活跃玩家全部离场后，此前已被淘汰的玩家排名成为 `1-1` 且状态为 `ELIMINATED`）中，HTTP 接口返回权威 `championPlayerId: null`，而内存快照通道会误将该已淘汰玩家标记为冠军，造成刷新前后双通道赛果不一致。原有测试仅覆盖了并列淘汰（`placement: { from: 1, to: 2 }`）的无冠军场景，未覆盖单一已淘汰玩家 `1-1` 的场景。 | **P1** | **已修正**：收紧 `snapshotChampionPlayerId` 判定条件，要求第一名候选玩家必须满足 `pokerStatus === "ACTIVE"`。在 `result-view.test.ts` 中新增单一 `ELIMINATED` 玩家排名 `1-1` 时不标记冠军且 `resultChampion` 返回 `hasChampion: false` 的单元回归测试。 |
| **F-02** | Codex [`4033991246`](https://github.com/fujiabao89/Texas-Holdem/pull/57#discussion_r4033991246)：Cache the fast-path snapshot before it is replaced | **有效**。当房主在原桌点击“再来一局”开启下一局比赛后，WebSocket 投影的 `state.game` 会被新比赛快照替换，导致停留在旧赛果页面的玩家其 `matchingSnapshot` 变为 `null`。若未就地缓存该快照，组件会触发 HTTP 重查，若遇临时 503 或网络抖动，原本已正确呈现的赛果会突变为错误屏幕，破坏多轮开局的隔离契约。现有测试仅断言了手动注入的 `cache` 记录，未覆盖组件生命周期对实时快照的自动固化。 | **P2** | **已修正**：在 `ResultPageContent` 中增加 `useEffect`，一旦观测到匹配的终局快照 `matchingSnapshot`，立即固化缓存至 `recoveredResults[tournamentId]`，避免被后续轮次快照置换或引发非必要的网络查询。 |
| **F-03** | Codex [`4033991249`](https://github.com/fujiabao89/Texas-Holdem/pull/57#discussion_r4033991249) / Greptile [`4034048430`](https://github.com/fujiabao89/Texas-Holdem/pull/57#discussion_r4034048430)（同义合并）：Clear stale request errors when an active result becomes available | **有效**。若某次 HTTP 获取赛果失败设置了 `error`，随后若通过 WebSocket 接收到匹配快照、或路由切换至已缓存赛果的比赛时，`useEffect` 判定 `activeResult` 存在而提前 return，导致旧 `error` 未被清空；加之渲染分支中 `if (error !== null)` 处于 `activeResult` 之前，导致有效赛果被已过期的错误屏幕永久遮挡。 | **P2** | **已修正**：(1) 渲染门禁调整为 `if (error !== null && activeResult === null)`，只要赛果有效绝不展示报错；(2) 路由参数 `[roomId, tournamentId]` 变更时重置 `error`；(3) 恢复流程检测到 `activeResult` 存在时主动执行 `setError(null)` 清理过期错误。 |
| **F-04** | Greptile [`4034048421`](https://github.com/fujiabao89/Texas-Holdem/pull/57#discussion_r4034048421)：Result ranks change after reload | **无效 / 越权**。Greptile 认为无冠军终局中快照保留原始名次而持久化赛果压缩名次，建议在客户端统一重排。依据《多 Agent 协作总约束》第 2 条与 docs/05 §16，“排名、名次（含并列区间）与最终筹码全部来自服务端，客户端严禁计算或重排赛果”，客户端无权对名次重新裁决；且随着 F-01 修复，快照通道与 HTTP 通道的名次与冠军状态已完全对齐。 | **P3** | **跳过**：纯服务端规格与客户端架构红线冲突，客户端严禁违背权威名次进行私自重排。 |
| **F-05** | Greptile [`4034048438`](https://github.com/fujiabao89/Texas-Holdem/pull/57#discussion_r4034048438)：Client derives the champion | **无效 / 投机性重构**。Greptile 声称客户端不能从快照推导冠军，必须在协议 `GameSnapshot` 增加显式 `championPlayerId`。`GameSnapshot` 是牌桌实时运行的通用投影协议（docs/02 §9），本任务为 Web 端接入赛果恢复，无权擅自更改协议 Schema 破坏已有端点兼容性；且读取服务端已给出的唯一第 1 名并核实活跃状态属于纯数据展现适配，并非在客户端计算牌局胜负。 | **P3** | **跳过**：超出本任务范围，且违背不得以代码隐式修改协议规格的协作契约。 |
| **F-06** | Codex [`4036918781`](https://github.com/fujiabao89/Texas-Holdem/pull/57#discussion_r4036918781) / CodeRabbit（PR 会话）：Keep rankings consistent across reloads / 内存快路径与刷新恢复仍显示不同名次 | **有效**。在先淘汰一名玩家、随后活跃玩家全部撤回（WITHDRAWN）的合法无冠军终局中，引擎内部生成的 `finalStandings` 保留了该淘汰玩家的原始原桌名次（如 `{ from: 3, to: 3 }`）；持久化赛果端点 `tournament-result.ts` 经 `compactPublicStandings` 将排除撤回玩家后的剩余名次压缩为公开连续排名 `{ from: 1, to: 1 }`，而实时投影器 `state-projector.ts` 此前直接将 `state.finalStandings` 原样映射为 wire `GameSnapshot.rankings`。导致赛果页在首次展示实时快照时显示第 3 名，刷新页面或直接访问拉取持久化结果时变为第 1 名。此前测试 `tournament-result-read.test.ts` 仅断言了持久化结果的名次，未断言快照与持久化名次的双通道一致性。 | **P1** | **已修正**：将 `compactPublicStandings` 设为公开导出函数，`state-projector.ts` 中的 `projectRankings` 与 `TOURNAMENT_FINISHED` wire 事件投影均统一接入 `compactPublicStandings`；实时快照与持久化赛果的名次压缩规则完全对齐。在 `state-projector.test.ts` 增加单元测试，并在 `tournament-result-read.test.ts` 真实淘汰+撤回集成测试中补充 `expect(f.view().rankings).toEqual(result.json().data.rankings)` 双通道严格对齐断言。 |
